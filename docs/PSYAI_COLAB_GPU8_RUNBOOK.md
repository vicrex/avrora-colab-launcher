# PSYAI Colab GPU8 — закреплённый способ запуска и проверки (18.11.2026)

## Цель и границы

- PSYAI занимается **неклинической психологией**. Любые психологические трактовки — **рабочие гипотезы**, не установленная истина.
- CASE34 содержит 34 синтетические реплики. Полный CASE34 E2E и данный однофразный GPU preflight — **разные тесты**.
- Этот конкретный workflow проверяет ТОЛЬКО аппаратную/программную возможность запуска Gemma 4 12B Q4 на GPU при бюджете VRAM до 8192 MiB. Он не измеряет полноценный CASE34 и не подтверждает цель 10–15 минут.

## Проверенный способ оркестрации (без браузера, без повторной авторизации)

1. Репозиторий запуска: `vicrex/avrora-colab-launcher`, ветка `main`.
2. Workflow: `.github/workflows/psyai-gpu8-colab-one-shot.yml`. Он использует уже существующий секрет `AVRORA_COLAB_ADC_JSON_B64` (не печатать, не сохранять в артефакты). Клиент: `google-colab-cli==0.7.4`.
3. CLI: `colab --auth=adc run --gpu T4 --timeout 2100 tools/psyai_case34_gpu8_colab_probe.py`. Никакого браузера и дополнительной авторизации. `--timeout 2100` — 35-минутный **таймаут исполнения удалённой ячейки**, а не гарантия выделения GPU.
4. Bridge: `tools/psyai_gpu8_colab_bridge.py` запускает CLI, читает его вывод, **показывает только безопасные маркеры этапов**, ограничивает ожидание до 40 минут, записывает `psyai_gpu8_proof.json`. Детальные журналы сторонних инструментов в GitHub не публиковать. Если Colab CLI не отдаёт промежуточный поток, отметки этапов появятся только по завершении — не выдавать это за подтверждение зависания Gemma.
5. Colab-скрипт: `tools/psyai_case34_gpu8_colab_probe.py`. NVIDIA T4, PyTorch-резерв лишней VRAM после создания CUDA-контекста, проверка доступного бюджета и PID-watchdog, скачивание pinned Gemma GGUF, сверка SHA-256, сборка `llama.cpp` с `GGML_CUDA=ON`, простой контрольный вопрос (ожидаем «маяк»). Параметры inference: `-ngl 20 -c 2048 -b 256 -ub 128 -n 32`.
6. Модель: `google/gemma-4-12B-it-qat-q4_0-gguf`; revision `ef7b15515d7ed7f34305a08edb5717e7989d6dc9`; файл `gemma-4-12b-it-qat-q4_0.gguf`; SHA-256 `93567e57a8fe10b23569b9d9ec38cd005deedf71e29477c421a4b83f418a538b`.
7. Если старый диагностически слепой GPU workflow висит, **новый workflow с `cancel-in-progress: true` в той же concurrency group** отменяет старый и устаревшую pending-очередь. Проверить фактический статус старого и нового через GitHub runs API; не говорить «остановлен», пока GitHub не подтвердит cancellation.
8. После каждого прогона смотреть подтверждённый статус GitHub run/job, `psyai_gpu8_proof.json`, `PSYAI_GPU8_STATUS`, список этапов и времена, пик модели. При отсутствии valid receipt — **FAIL / INCOMPLETE**, а не PASS. Ошибки журнального API `404 BlobNotFound` не означают сбой CUDA.
9. Использовать `tools/psyai_gpu8_colab_bridge.py` во всех новых GPU preflight workflow. Не повторять старую конструкцию `colab ... > remote.log 2>&1`, которая скрывает этапы и ошибки до завершения.
10. После успешного GPU preflight отдельно подготовить и выполнить **полный приватный CASE34** на Gemma + E5 + граф + NLI/V2, со сверкой всех 34 реплик, атрибуции и доказательств `SUPPORTED`, отчётами и таймингом. Факты — только о содержимом реплик; все психологические интерпретации — гипотезы. Не подменять это контрольным вопросом о маяке.

## Защита ресурсов и честная отчётность

- Один GPU preflight за раз. Не запускать повторы параллельно.
- Не строить EXE, не запускать Bybit/AVRORA trading, не загружать клиентские данные в публичный репозиторий.
- Публиковать только исходный код и sanitised proof, не ADC/токены/сырой stdout.
- Colab T4 с ограниченной свободной VRAM **не эквивалентен RTX 4060 по скорости**, проверяется в основном память и функциональность. 8 GiB — доступный GPU memory budget, не точная аппаратная эмуляция.
- У каждого длительного этапа должны быть `START/PASS/FAIL/TIMEOUT`, elapsed и reason code.
- Не утверждать «модель загружена», пока `pinned_model`/инференс не подтверждены заверенным receipt.

## Обязательная последовательность с 18.11.2026 (независимый журнал)

1. Изменения вносить в исходники **до** запуска. Проверить syntax `py_compile` и наличие правил `8192 MiB`, SHA модели и `case34_full_e2e=False`.
2. Требовать `contents: read` и `statuses: write` в GitHub Actions; `GITHUB_TOKEN` передавать **только** локальному `tools/psyai_gpu8_colab_bridge.py`, никогда — процессу `colab`, удалённому ноутбуку и артефактам.
3. До открытия удалённого Colab выполнить тестовую запись commit status `psyai-gpu8/heartbeat`. **Если запись в GitHub не прошла, завершить локально ошибкой `STATUS_JOURNAL_UNAVAILABLE`**, не создавать дорогостоящую GPU-сессию.
4. После успешной проверки запускать один Colab CLI: `colab --auth=adc run --gpu T4 --timeout 2100 tools/psyai_case34_gpu8_colab_probe.py`. Ограничить выполнение bridge 40 минутами, GitHub job 45 минутами; отдельный 85-минутный общий таймаут — запас на подготовку.
5. Пока bridge работает, посылать в commit status `psyai-gpu8/heartbeat` сигнал раз в 60 секунд; в сообщении `waiting_for_colab_output` не утверждать, что GPU выделен или модель загружена. Когда CLI отдаёт маркеры, публиковать `psyai-gpu8/stage/<name>`: `START/PASS/FAIL/TIMEOUT/BLOCKED`.
6. После завершения сохранять SHA-проверенный `psyai_gpu8_proof.json` и терминальный статус. При отсутствии заверенного receipt — `INCOMPLETE/FAIL`, **не PASS**. Смотреть на сам run, но при `404 BlobNotFound` для Actions job logs читать **commit statuses** через `GitHub -> commit -> Statuses` или GitHub REST `GET /repos/vicrex/avrora-colab-launcher/commits/<HEAD_SHA>/statuses`.
7. `cancel-in-progress: true` для группы `psyai-colab-cpu-global-nonparallel` отменяет старый параллельный запуск при новом `push` в файл workflow. Проверить старый run `conclusion=cancelled` **отдельно**, перед заявлением об остановке. Не запускать новые дубли.
8. Зафиксировать подтверждённый пик VRAM, время загрузки/сборки, время inference и `generation_verified`. Затем, **в отдельном запуске**, проводить приватный E2E CASE34 (34 синтетические реплики, неклинические психологические гипотезы, E5 + граф + NLI, все `SUPPORTED` с цитатой, целевое 600–900 секунд) — не выдавать canary «маяк» за полный анализ.

**Гарантия наблюдаемости имеет границу:** GitHub heartbeat подтверждает работу *локального процесса bridge*. Статус GPU/модели подтверждается **только** маркерами Colab и валидным удалённым receipt. Если CLI буферизует stdout, commit statuses смогут показывать только `waiting_for_colab_output`. Для настоящей телеметрии внутри Colab может потребоваться отдельный удалённый канал или CLI streaming.

## Подтверждённые ошибки, официальные источники и запреты на повторение (18.11.2026)

1. **Официальное поведение CLI.** В `google-colab-cli==0.7.4`, `src/colab_cli/commands/run.py` функция `run_command` принимает `gpu` (`--gpu T4`) и `timeout` (`--timeout`) со значением **30.0 секунды по умолчанию**. Поэтому в `tools/psyai_gpu8_colab_bridge.py` необходимо явно передавать `--timeout 2100` для длительной загрузки модели, CUDA build и генерации. Источник: https://github.com/googlecolab/google-colab-cli/blob/v0.7.4/src/colab_cli/commands/run.py ; документация: https://github.com/googlecolab/google-colab-cli/blob/main/docs/05_run_command.md .
2. **Ошибка собственного пре-флайта.** GitHub run `44233223824` завершился FAIL на шаге `Preflight Colab CLI GPU run syntax`: код искал текст `--gpu` **обязательно в stdout**, хотя справка CLI может идти в stderr или форматироваться. Это **ложноотрицательная проверка**. Теперь вместо разбора `--help` проверяем установленную версию пакета `google-colab-cli==0.7.4` и сигнатуру `colab_cli.commands.run.run_command` на параметры `gpu` и `timeout`, не выделяя GPU.
3. **Предыдущий быстрый отказ.** Run `44232378197` завершился FAIL: процесс Colab CLI вышел с кодом `1`, из-за отсутствия удалённой receipt запись была `COLAB_NO_VERIFIED_REMOTE_RECEIPT`. Затрачено около **2.31 секунды внутри bridge**, GPU/модель не подтверждены. Это **НЕ доказательство, что причина в 30-секундном timeout**, потому что отказ произошёл раньше. Код классификации исходящего CLI обновлён; требуется новое подтверждение из реального прогона.
4. **Надёжный порядок действий.** (a) сверить GitHub статусы всех предыдущих запусков и отсутствие активных дублей; (b) подготовить и сохранить код и инструкции, выполнить static validation и проверку версии CLI; (c) проверить независимую запись `psyai-gpu8/heartbeat`; (d) запустить единичный `colab run --gpu T4 --timeout 2100`; (e) каждые 60 секунд публиковать heartbeat, при получении этапов — отдельные статусы; (f) записать `psyai_gpu8_proof.json`, SHA-256 receipt, код выхода CLI, задержки загрузки/сборки/inference, пик VRAM; (g) проверить `status=completed`, `conclusion`, receipt и результаты; (h) только потом отдельный полный CASE34 (34 синтетические реплики, неклинические психологические гипотезы, E5+граф+NLI/V2 и 10–15 мин). Не заявлять об успешном GPU preflight/CASE34 без receipt.
5. **Контроль ресурсов.** `concurrency.cancel-in-progress: true` в GitHub workflow отменяет прежний запуск при новом запуске в той же группе. Это не заменяет проверки, что предыдущий GitHub run реально `conclusion=cancelled`. Не перепутать отмену локального GitHub job с подтверждённым освобождением удалённой Colab GPU-сессии; по возможности проверять `colab sessions` с тем же ADC, но не уничтожать чужие сессии.
6. **Контроль наблюдаемости.** `tools/psyai_gpu8_status.py` использует отдельные статусы коммита GitHub (право `statuses:write`), не зависит от `BlobNotFound` журнала Actions. Начальный статус должен быть успешно записан **до** выделения GPU. В `waiting_for_colab_output` нет доказательств запуска модели, даже если каждую минуту есть heartbeat.
7. **Безопасность и предметная область.** ADC из `AVRORA_COLAB_ADC_JSON_B64`, GitHub token только локальному журналу, не печатать и не передавать в Colab. Прогон не связан с Bybit/торговлей. PsyAI — **неклиническая психология**, психологические выводы — **гипотезы**, тестовые диалоги CASE34 — синтетические.

### Текущий критерий PASS

`GPU8_MODEL_PREFLIGHT_PASS` допустим **только** если в SHA-проверенной удалённой receipt отражены T4, модель с правильным SHA-256, фактический GPU-пик в бюджете 8192 MiB и успешная canary-генерация. Всё остальное — `FAIL`, `BLOCKED` или `INCOMPLETE`. Отдельно `CASE34_FULL_E2E_PASS` не предусмотрен этим тестом и должен подтверждаться отдельной приёмкой.
